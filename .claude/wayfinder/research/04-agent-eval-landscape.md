# Research 04 — How coding agents and multi-agent orchestration are evaluated, and what transfers to maestro

<!-- ticket: tickets/004-research-how-agent-orchestration-is-evaluated.md -->
<!-- researched: 2026-09-18 -->

## Summary

1. Every credible coding benchmark grades **end state**, not trajectory: tests that must flip fail→pass plus tests that must stay passing (SWE-bench), a container state a test script accepts (Terminal-Bench), or a database compared against an annotated goal state (τ-bench). Anthropic's own guidance agrees: "Grade what the agent produced, not the path it took."
2. The SWE-bench family is a cautionary tale, not a template. OpenAI publicly retired SWE-bench Verified in Feb 2026 for contamination plus defective tests. Public task sets are the wrong core for maestro's set.
3. **Nothing mainstream measures an orchestrator end-to-end on long dev work.** The closest pieces are SWE-EVO (multi-file evolution), TheAgentCompany (checkpoint partial credit + simulated colleagues), and Terminal-Bench/Harbor (native multi-step task format, cost and token columns, CIs).
4. Cost reporting is the settled part of the field: HAL, Aider, Terminal-Bench, SWE-rebench and Artificial Analysis all publish dollars; the canonical SWE-bench leaderboard still does not. Report dollars **and** tokens so figures survive price changes.
5. Statistics are the unsettled part. HAL spends ~$40k on 21,730 rollouts and publishes no error bars. Terminal-Bench (multiple trials, 95% CIs, task-clustered bootstrap) is the only mainstream leaderboard doing dollars *and* uncertainty.
6. For an unattended orchestrator the honest accuracy metric is **pass^k** (all k trials succeed), not pass@k. MLE-bench's 16.9% pass@1 → 34.1% pass@8 is the clearest illustration of how much pass@k flatters.
7. **The result that most threatens maestro's premise**: at equal thinking-token budget, single agents match or beat multi-agent systems (arXiv 2604.02460), and Anthropic's own multi-agent post concedes token usage explains ~80% of its performance variance. Any orchestrator-vs-bare-session comparison that does not equalise or report cost is refuted in advance.
8. **MAST** (Berkeley, arXiv 2503.13657) is the best single citation in this space: 14 failure modes from 1,600+ annotated traces, 41–86.7% failure rates across 7 frameworks, with specification/design 41.8%, inter-agent misalignment 36.9%, verification 21.3%. A failure taxonomy is the diagnostic layer a score cannot give you.
9. Harness-vs-model work (2026) shows scaffold choice moves token cost up to 40x at 0–8 points of pass rate. Accuracy alone will not separate maestro's lineages; cost will.
10. `claude plugin eval` already implements the two-arm with/without-plugin ablation, 3 runs per case, 6 grader types, USD cost, a cost ceiling and a CI exit code — the cheapest credible start. `skill-creator` is the right *shape* but structurally unfit: no fixture, no test execution, contaminated baseline, hand-copied tokens, "± 0%" for n=1, and a sign-flipped delta in improve mode.

## What transfers to evaluating an orchestrator inside Claude Code — and what does not

The object under test is a **protocol** (prompt + skills + agents + hooks) with the models held fixed. Not a model. That single fact decides most of the list.

### Transfers

- **Two-arm ablation with a declared baseline.** `claude plugin eval`'s with/without-plugin Δ and `skill-creator`'s `with_skill`/`without_skill` are the same idea and it is the right one: a high absolute score proves nothing if a bare session scores the same. For maestro the comparison is three-way (lineage A vs B vs C) plus a bare-session floor.
- **Excluding non-comparable graders from the score.** Plugin eval's rule — a `tool_used: Skill` check can never pass in the baseline arm, so counting it would push the baseline toward zero and inflate Δ — applies verbatim. "The hub delegated to a lane", "the tracker was updated", "a worktree was created" are *protocol-conformance indicators*, reported beside the score, never inside it.
- **End-state ground truth with an explicit must-not-break set.** `FAIL_TO_PASS` + `PASS_TO_PASS` maps onto a fixture repo: acceptance tests written for the task, plus the fixture's pre-existing suite as the regression guard. τ-bench's "final DB equals annotated goal state" maps onto repo/tracker state assertions. Terminal-Bench's contract — a verifier that writes a numeric reward, plus a human-written oracle solution that must pass — is worth copying literally; the oracle is what catches unsolvable or misspecified cases before they poison a baseline.
- **Checkpoint partial credit for long tasks.** TheAgentCompany's per-checkpoint programmatic evaluators and PaperBench's 8,316-item author-co-designed rubric are the two published answers to "how do you grade hours of work that has no single test". Anthropic says the same: "For tasks with multiple components, build in partial credit." Binary success on a multi-task GOAL throws away almost all the signal.
- **pass^k over pass@k.** An orchestrator that runs unattended is judged on consistency. pass@k is gameable — a temperature-ramping retry loop hit 93.2% on HumanEval at $2.45, statistically indistinguishable from LATS at 88.0% and $134.50 — and is ceilinged by verifier false positives regardless of budget. MLE-bench's 16.9% → 34.1% is the size of the flattery.
- **Dollars *and* tokens, reported separately from accuracy.** Pareto front first; a weighted scalar only when a decision needs one. Report raw token counts per model so figures survive price changes.
- **Equalised or explicitly reported compute in any orchestrator-vs-single-agent claim.** This is not optional. At equal thinking-token budget, single agents match or beat multi-agent systems across three model families (arXiv 2604.02460), with an information-theoretic argument behind it: when the hub hands a brief to a lane, the lane works from a *processed* context, so information can only be lost. Anthropic's own multi-agent post reports a 90.2% win over single-agent Opus 4 while conceding that **token usage alone explains ~80% of its performance variance** and the system burns ~15x a chat's tokens. maestro's whole value proposition sits exactly on this fault line, so the harness must be able to answer "same accuracy at what cost" before anything else.
- **Repetitions plus paired statistics, with the MDE computed before the run.** Miller's formulas give both: `SE = sqrt(s̄(1−s̄)/n)` for binary scores, paired SE on per-case differences, and `δ = (z_{α/2}+z_β)·sqrt((ω² + σ²_A/K_A + σ²_B/K_B)/n)` for the minimum detectable effect. Pairing on the same case with the same models is free variance reduction; McNemar's paired required-N is a median 2.15x smaller than unpaired.
- **ICC as a sanity check on repetition count.** On GAIA L3 the intraclass correlation was 0.304 — ~70% of variance was trial-to-trial randomness, with convergence needing n≈8–32. If maestro looks like that, a 3-run benchmark is decoration. Vending-Bench makes the same point qualitatively: the interesting object is the derailed run, not the mean.
- **Clean environment per trial.** Anthropic: "Each trial should be isolated by starting from a clean environment." Plugin eval enforces it hard — no user settings, no `CLAUDE.md`, no other plugins, no project `.claude/`.
- **Grader mix, deterministic first, judge validated separately.** Code-based graders wherever possible; LLM judge only for what code cannot check; calibrate the judge against human verdicts on a subset (PaperBench benchmarks its judge as a separate artifact). Anthropic's own reversal is the argument: Opus 4.5's CORE-Bench score moved from 42% to 95% after grading bugs were fixed.
- **A cost ceiling and honest partial results.** `--max-cost-usd` plus a `partial` flag that excludes the run from trend charts. "AI Agents That Matter" notes SWE-bench runs cost $8,000+, which is exactly why error bars are "rarely" reported.
- **Harness pinning.** Pin model IDs, reasoning effort, Claude Code version, plugin commit. Scaffold choice induces up to 40x differences in tokens per solved task at 0–8 points of pass rate; an unpinned model rollout will read as a plugin regression. Terminal-Bench's practice of labelling every row as (agent × model) rather than "the model" is the honest convention.
- **A failure taxonomy alongside the score.** MAST's three categories are a ready-made classification scheme for maestro's post-mortems, and its distribution is a prior worth holding: specification and system design 41.8%, inter-agent misalignment 36.9%, verification 21.3%. Two of its named modes — step repetition and premature termination — are precisely the failures v4's verification step and `orchestrate`'s escalation ladder claim to prevent, so they should be first-class labelled outcomes in the harness, not free-text notes.

### Does not transfer

- **Absolute scores and cross-system comparability.** maestro will never produce a leaderboard-comparable number. The deliverable is a *relative* verdict between iterations on one private set — closer to A/B regression testing than capability measurement. Stop reporting anything that implies otherwise.
- **"New evals should contain at least 1,000 questions."** Miller's worked example needs n≈969 to resolve a 3-point difference. At tens of minutes and single-to-double-digit dollars per orchestrator run, that is off by two orders of magnitude. The available moves: push power into repetitions K and pairing rather than n; use graded/checkpoint scores instead of binary; and refuse to claim improvements below the computed MDE.
- **Contamination as a model problem.** We train nothing. Contamination bites only via the *task set*: if fixtures come from public benchmarks, the models have likely seen the answers and the measurement drifts from "did the protocol help" to "did the model recall". Historical Iconsulting MRs and purpose-built fixtures are contamination-free by construction; public benchmark subsets are not.
- **"Grade the outcome, not the path" — only half applies.** For a model the path is incidental. For an orchestrator part of what is under test *is* the path: did the hub delegate, verify before closing, stop at the gate, leave an honest tracker. The resolution is not to score the trajectory as accuracy but to carry a second, separately reported axis of protocol conformance (plugin eval's `tool_used` / `tool_order` graders are exactly this) and keep it out of the accuracy number. Aider's "percent using correct edit format" column is the precedent for reporting protocol compliance as its own metric.
- **Single-run, single-turn harness assumptions.** `claude plugin eval` is non-interactive with `max_turns` ≤ 200 and `timeout_seconds` ≤ 3600 per run. A multi-goal hub session that spawns lanes, uses worktrees, compacts context and stops for approval does not fit. Seeding prior conversation via `context.history_file` buys one extra user turn, not a dialogue.
- **The Windows assumption.** Any plugin-eval suite granting Bash runs under Claude Code's OS-level sandbox, and "Native Windows has no backend" — such suites must run under WSL2. That collides with .NET/Windows fixture coverage (ticket 2).
- **LLM-as-judge as the primary accuracy oracle for code.** Position bias alone shifts pairwise accuracy by >10 points; prompt-induced biases are "large enough to change task-level conclusions and alter relative model rankings"; a same-family judge inflates its own family by ~+0.75 on a 7-point scale; and on near-equal candidates a judge promotes the worse one 31% of the time. maestro's iterations will be near-equal by construction. The judge can find and describe defects; it must not declare the winner.
- **Simulated users as a faithful stand-in for the human.** Usable for *relative* comparison with the simulator frozen; not usable for any absolute claim about how much human attention maestro needs. Details below.
- **Benchmark version churn as an acceptable cost.** Terminal-Bench shipped four breaking versions in nine months, and v2.1's task fixes alone moved one agent +12.1%. maestro's own case set must be versioned and frozen per measurement campaign, with fixes creating a new version rather than silently editing the old one — otherwise the baseline stops meaning anything.

## Handling the human in the loop

All three lineages stop for the user (goal approval, product questions, the end-of-task gate), so this is on the critical path of every run, not an edge case. The literature offers five options and no clean one.

| Option | How it works | What it buys | Its bias |
|---|---|---|---|
| **1. LLM user simulator with hidden intent + policy** (τ-bench, τ²-bench) | An LLM gets a natural-language intent the agent never sees, plus a domain policy document; it replies turn by turn from the conversation history | The only option that exercises goal negotiation and question quality end to end. τ²'s dual control shows how much it matters: guiding a counterparty costs 18–25 pass^1 points | **~14 points of inflation** vs 451 real humans on τ-bench. Four measured divergences: politeness (49% vs 15%), **front-loading all details upfront instead of disclosing incrementally**, mis-calibrated clarification, polite pivots instead of frustration. Simulators **never disengage** (48% of the human rate; resistance 25.1%→13.5%) and **the simulator model choice alone moves agent success by up to 9 points**, with worse validity for AAVE and Indian English speakers |
| **2. Auto-approver** (ERPBench's benchmarking mode: "an auto-approver approves every action across all risk tiers, so a full task runs without a human") | Every gate is granted instantly | Deterministic, free, reproducible | Measures the system **as if the gate did not exist**. Cannot score whether the agent asked at the right moment, batched sensibly, or asked at all |
| **3. Canned answer table with a `proceed` default** | A fixed question→answer map; unmatched questions get the default | Zero judge noise, perfectly reproducible across iterations — the strongest property for comparing lineages | Biases toward orchestrators that ask **predictable, anticipated** questions and penalises ones that probe usefully in an unanticipated direction. The map is itself a hidden spec |
| **4. Evaluate only the AFK segment** (approved GOAL → done) | Cut the human out of the measured window; start from an already-approved goal with pre-granted authorizations | Removes the confound completely; cheapest defensible design; closest analogue to SWE-bench | Measures nothing about goal negotiation, gate behaviour or interruption handling — a large fraction of what v4 §3 and `orchestrate`'s "after every completed task, stop and ask" actually specify |
| **5. Live human on a small subset** (Anthropic's manual testing; CollabLLM's 201 real users; the sim2real study's 451 participants) | A person plays themselves on a handful of cases | The only calibration source for options 1–3. Anthropic: "Manual testing proved essential for catching edge cases automation missed" | Does not scale to iteration volume; and one person reviewing their own plugin is confirmation bias — which is exactly `skill-creator`'s review loop |

**Scoring the human load.** The literature is consistent that this is a separate axis, never folded into accuracy:

- **HITL load** = total human interventions across successfully completed tasks; **TCR@k** = share of tasks completed with at most k interventions, so **TCR@0 is the fully-autonomous rate**. Defined in a security/autonomy context (arXiv 2602.11416, demonstrated on AgentDojo), but the definitions are domain-neutral.
- **Ask-F1** (HiL-Bench) = harmonic mean of question precision and blocker recall, designed to penalise **both** over-asking and silent guessing. This answers ticket 3's "is a question a cost or a quality signal": it is both, and Ask-F1 is the shape that stops the two from cancelling.
- Anthropic's operational version of the same idea: Claude Code's internal success rate on the hardest tasks doubled from August to December while **average human interventions per session fell from 5.4 to 3.3**. That is the template for a longitudinal number — interventions per session reported *alongside* success, not netted against it.

**The honest gap.** No published benchmark scores an agent's behaviour *at* an approval gate with a simulated reviewer. ERPBench, the closest thing, auto-approves during benchmarking. If gate quality turns out to be a decisive design axis between the lineages, maestro will be inventing that measurement, not borrowing it — budget for that.

**Recommendation.** Option 4 (AFK segment) as the default measured window, because it is the only way to get a clean accuracy/cost signal at an affordable sample size. Option 3 (canned answers with a `proceed` default, frozen and versioned with the harness) layered onto the cases that must exercise gates, with the number of times the default fired reported as a coverage metric. Option 5 on a fixed 5-case subset per iteration purely to calibrate. Option 1 only if question quality becomes the decisive axis — and if so, pin the simulator model and prompt into the harness version number, and use a **staged-disclosure** policy (reveal on request, never upfront) to counteract the measured front-loading bias.

## Three candidate harness designs

Common to all three: models pinned (ID + effort), Claude Code version pinned, plugin commit pinned, one frozen fixture state per case, an oracle solution proving each case is solvable, ≥3 runs per case per iteration, paired per-case differences, and the MDE computed and stated *before* the run.

### Design A — `claude plugin eval` on the AFK segment

Use the built-in harness as-is. Each case is a directory with `prompt.md` (an already-approved GOAL plus task brief; `max_turns: 200`, `timeout_seconds: 3600`, `allowed_tools` including `Task`/`Skill`/`Bash`), a `case.yaml` whose `context.scaffold_script` materialises the fixture repo, and graders under `graders/`: `regex` over a test-output file the prompt asks the agent to write, `tool_used`/`tool_order` for protocol conformance (marked so they don't inflate Δ), `file_exists` for expected artifacts, one `llm` grader on a short summary. Run with `--ablation with-without --runs 3 --threshold <t> --max-cost-usd <cap> --json --no-publish` and gate on the exit code.

- **Effort:** low — days. Zero harness code; `claude plugin eval init` drafts the suite.
- **Cost per run:** bounded by construction (≤1 h, ≤200 turns), reported in USD by the tool, with a hard ceiling.
- **Detects:** whether the protocol triggers at all on natural phrasing; protocol conformance; the delta against a bare session; regressions between plugin versions and across model rollouts. Good enough to be the permanent CI gate (the "continuous evaluation" open question).
- **Cannot detect:** anything over 1 h or 200 turns; multi-goal sessions; approval-gate behaviour (non-interactive); context exhaustion, handoff and resume; human intervention counts; per-lane cost attribution (`COST` is per case, not per subagent) — which is the one number the multi-agent literature says decides the question.
- **Sharp edges:** must run under WSL2 once Bash is granted, conflicting with Windows/.NET fixtures. Isolation strips `CLAUDE.md`, user settings and other plugins, so any lineage relying on a per-repo binding file must ship it in the fixture or create it in the scaffold script.

### Design B — own runner over headless Claude Code, with OTel cost capture and a scripted user

A small runner drives one headless session per run, with a separate process playing the user from a hidden intent document under a frozen answering policy. Cost and tokens come from Claude Code's native OpenTelemetry export — `claude_code.cost.usage` (unit: **USD**) and `claude_code.token.usage`, attributed by `model`, `query_source` (`main`/`subagent`/`auxiliary`), `agent.name`, `skill.name`, `plugin.name`, `effort` — giving per-lane, per-model cost attribution essentially for free (`CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_LOG_TOOL_DETAILS=1`). Grading: fixture acceptance tests + the pre-existing suite as regression guard + repo/tracker state assertions + checkpoint partial credit + an independent review agent counting defects + one calibrated LLM judge on the diff. Outcomes labelled against MAST's three categories.

- **Effort:** high — weeks, and you own every bug in it. "AI Agents That Matter" traces most agent-eval irreproducibility to bespoke harnesses, including papers whose reported scores exceeded the maximum of their own five reruns.
- **Cost per run:** the budget line for the whole effort. A multi-task GOAL is tens of minutes to hours of model time; assume single-to-double-digit dollars per run, so `cases × 3 runs × 3 lineages × iterations` decides affordability. Calibration: HAL spent ~$40k for 21,730 rollouts on tasks far shorter than these.
- **Detects:** everything A detects, plus interventions and gate behaviour, context handoff and resume, rework rounds, wall clock, and **per-lane token/dollar split** — the decisive number given that harness choice moves cost 40x and accuracy 0–8 points, and that single-agent beats multi-agent at equal token budget.
- **Cannot detect:** real human friction. Cannot support absolute claims about human load, because the simulator inflates success ~14 points and never disengages.

### Design C — historical MR replay with an offline judge, no live user

Cases are real merged MRs from Iconsulting GitLab, extracted with `glab` and replayed at the parent commit. GOAL text derives from the MR description; approvals are pre-granted. Ground truth is the MR's own tests plus the project pipeline, with the merged diff used only as a *reference solution* for a judge scoring intent coverage and over/under-scoping — never diff equality, since the merged MR is one valid solution among many.

- **Effort:** medium — extraction is scriptable and case authoring is mostly free, which is what makes the set large enough to matter statistically.
- **Cost per run:** same agent cost as B, minus simulator cost and minus manual case authoring.
- **Detects:** accuracy and cost on *realistic* tasks in the stacks that matter; whether a lineage over- or under-scopes relative to what a human shipped; contamination-free by construction.
- **Cannot detect:** goal negotiation, gate behaviour, anything about the human loop. Constrained by client-code confidentiality (ticket 2). Historical MRs also carry survivorship bias — they are the tasks that got merged, so abandoned and ambiguous work is absent, which is exactly the class where an orchestrator's negotiation behaviour matters most.

### Trade-off call

C is the accuracy/cost workhorse and where the statistical power has to come from; A is the permanent cheap CI gate and the only thing still runnable per commit; the human loop starts as a frozen canned-answer table plus a 5-case live-human calibration subset. Escalate to B only if the baseline shows that gate behaviour, context exhaustion or per-lane cost attribution — not code correctness — is what separates the lineages. Do not build B first: the field's own record says bespoke harnesses are where reproducibility goes to die. And whichever design ships, the first report must include a bare-session arm at comparable token spend, because without it the multi-agent literature refutes the premise before the measurement starts.

## The `skill-creator` harness pattern, and where it falls short

**What it does.** For each eval prompt it spawns two subagents in the same turn — one with the skill, one without (or against a snapshot of the old skill when improving). Results land in `<skill>-workspace/iteration-N/eval-<id>/{with_skill,without_skill}/run-M/`. Assertions ("expectations") are natural-language statements graded by an LLM grader (`agents/grader.md`) that reads the transcript and output files and emits `grading.json` with `{text, passed, evidence}` per assertion, a `summary.pass_rate`, extracted-and-verified claims, and unsolicited critique of the assertions themselves ("a passing grade on a weak assertion is worse than useless"). `scripts/aggregate_benchmark.py` walks the run directories and emits `benchmark.json` / `benchmark.md` with mean/stddev/min/max of `pass_rate`, `time_seconds`, `tokens` per configuration plus a delta. An analyzer pass (`agents/analyzer.md`) flags non-discriminating assertions, high-variance evals and time/token trade-offs. A human then reviews outputs in an HTML viewer and leaves free-text feedback. An optional blind comparator does A/B judging.

**What is genuinely good and worth copying.** The paired with/without design in the same turn. The grader being told to fail superficial compliance ("correct filename but empty/wrong content") and to carry the burden of proof on the assertion. The analyzer's explicit hunt for assertions that pass in both arms — the "is this grader discriminating at all" check most harnesses skip. The instruction to read transcripts, not just outputs, and to bundle a script when three runs independently wrote the same helper.

**Where it falls short for long multi-agent runs with human-in-the-loop gates.**

- **No environment.** No fixture repo, no clean-room isolation, no test execution. Subagents run inside the parent session's environment, so the `without_skill` arm still carries the user's global `CLAUDE.md`, every other installed skill and plugin, and the parent's context. That is a **contaminated baseline** — precisely what `claude plugin eval` isolates against ("your user settings, hooks, `CLAUDE.md` files, MCP servers, other installed plugins, memory, and skills are absent").
- **No cost, only tokens, captured by hand.** `timing.json` is filled from the task-completion notification, and `SKILL.md` warns "this is the only opportunity to capture this data". No USD, no price model, no per-model or per-lane split — exactly the attribution a multi-lane orchestrator needs, and the axis the multi-agent literature says decides the question. Worse, `aggregate_benchmark.py` silently falls back to `execution_metrics.output_chars` when `timing.json` is missing and stores it in the same `tokens` field, mixing character counts and token counts in one column.
- **`pass_rate` is not a task success rate.** It is the fraction of assertions satisfied within a run, averaged over runs. A go/no-go on an orchestrator needs task-level success (and, per τ-bench, pass^k over repeated trials), not an assertion-satisfaction ratio that partial-credits a run which shipped broken code.
- **Statistics that overstate certainty.** `calculate_stats` returns `stddev: 0.0` for n=1, which `benchmark.md` renders as "± 0%" — reading as certainty where there is no sample. The default workflow spawns **one** run per configuration, yet `generate_benchmark` hardcodes `"runs_per_configuration": 3` into the metadata regardless. No CIs, no paired analysis, no power calculation, no MDE.
- **A sign-flipped delta in improve mode.** `aggregate_results` computes `delta = configs[0] − configs[1]`, where `configs` comes from `sorted(eval_dir.iterdir())`. For a new skill the directories are `with_skill` / `without_skill` and alphabetical order happens to be right. For **improving** a skill, `SKILL.md` says to save the baseline to `old_skill/` and the candidate to `with_skill/` — and `"old_skill" < "with_skill"`, so the reported delta is `old − new`, i.e. **backwards**. `SKILL.md` even instructs "put each `with_skill` version before its baseline counterpart", which the script's sort ignores.
- **Judge-only grading, unblinded, single-pass.** One grader, no second opinion, no human calibration, no inter-rater agreement — against a literature measuring >10 points of position-bias swing, ~+0.75/7 self-preference for same-family judges, and a 31% wrong-winner rate on near-equal candidates. And the grader reads a transcript that names the skill, so the arm leaks into the verdict. The blind comparator exists but is explicitly optional ("most users won't need it").
- **The human review loop is qualitative and self-graded.** Free-text feedback boxes, no rubric, no blinding, filled in by the person who wrote the skill. Fine for iterating on prose; not a basis for an architectural go/no-go.
- **No handling of human-in-the-loop gates at all.** A subagent that stops to ask a question simply stops, and the run is graded on whatever it happened to produce. No simulated user, no approval path, no intervention count.
- **Scale mismatch.** The design assumes a single-shot skill invocation of seconds to minutes (its schema example shows `duration_ms: 23332`). No cost ceiling, no wall-clock cap, no resume, and no notion of a run that spawns its own subagents — so a multi-lane, multi-hour orchestrator run has nowhere to put its per-lane numbers.

**Verdict.** Take the *shape* — paired arms, named discriminating assertions, a grader that critiques the assertions, an analyzer that hunts non-discriminating checks — and drop the *machinery*. `claude plugin eval` already supplies what it lacks: isolation, USD cost, a cost ceiling, `--runs`, arm-aware grader exclusion, and a CI exit code.
