## What Maestro becomes

Maestro, which so far held the orchestrator prompts v1–v4, becomes a **Claude Code plugin** that runs a multi-agent software team. The plugin source and its local marketplace live in this repository. Each project installs the plugin, keeps only its own data (tracker, decisions, reports, handoff) and its own rules (`AGENTS.md`), and launches its own dashboard. The plugin must **not depend on Paseo**: the owner uses Paseo as UI, so the plugin may use it when present, but it must work without it.

Authoritative design: `team-workflow/flusso-team-agenti.html` (draft v2, in Italian; open it in a browser). Read it in full: section 0 lists the owner's decisions, section 14 the open points (now resolved below), section 15 the rollout.

## Decisions taken by the owner (6 Nov 2026)

- Roles: owner (responsible for the project, not just an end user), PM (main session), architect (GOAL lead), 2 implementers, exploratory QA (black box, no code access), periodic code reviewer.
- D1: run agents as **Claude Code subagents** (nesting verified), not Paseo agents.
- D2: **Backlog.md** as tracker (confirmed by the bake-off below); beads only as fallback.
- D3: the **architect leads a GOAL**: decomposes it in waves, spawns and coordinates the implementers, reviews, resolves conflicts and integrates into `master`. The PM spawns QA and reviewer independently. **Start with one GOAL at a time**; parallelism is between the two implementers of the GOAL (each in its own worktree, integration branch per GOAL).
- D4: freeze an area during QA only for critical areas (persistence, migrations, file formats); elsewhere work on tagged snapshots and check finding validity at triage.
- Q1: the GOAL queue is defined with the PM; new ideas are placed into the current plan together. Q2: **deploy always on explicit owner request**. Q3: parallel independent GOALs allowed later, postponed until after the pilot. Q5: Sonnet by default, Opus for hard tasks, **never Fable**; the architect chooses model and effort per task. Q7: this replaces orchestrator v1–v4 (carry over v4's rules on authority, decisions, retries ≤2, critique cycles ≤2). Q8: no caps per agent but loop protection (maxTurns); the PM watches its own context and the 5-hour/weekly usage. Q9: periodic code review every 15 integrated tasks or at GOAL end, whichever first.
- A2: agents run in auto permission mode; if a permission prompt can surface, forward it to the owner. A3: separate test author postponed; until then the implementer writes tests, but the architect specifies acceptance cases (given/when/then) that must map 1:1 to named tests, the architect reviews tests first, code review checks test quality, QA is the final independent net. A4: framework in English, dialogue with the owner in the project's language.
- Decision governance: nobody chooses at random. Local reversible details → the worker; technical within an approved direction → architect with an ADR; **material** (new technologies/dependencies, database, cache, new architectural components, data formats, persistence, external services, security, costs, scope) → the owner via the PM, with 2–3 options and a recommendation; blocked tasks wait while other work continues.
- Planning in waves: future GOALs only have outcome/criteria; the architect details tasks when the GOAL starts, wave by wave, referencing symbols not line numbers; implementers preflight the spec against current code.
- Multi-PC: tracker, decisions, reports, handoff and events are in git; only runtime (locks, claims, heartbeats, caches) and worktrees are ignored. A "pause" skill brings everything to a clean committed point (WIP branches); push only with owner authorization; "resume" works after a clone.
- Old GOALs/tasks are archived, never deleted; PLAN.md stays short (vision, constraints, roadmap, index).
- Dashboard: local, read-only, code in the plugin, launched per project; views Roadmap (milestones → GOALs → tasks with dependencies), Board, Agents (who does what, since when), Decisions, Reports; shows PM context % and usage.

## Verified facts (research, all in `research/`)

- `claude-code-capabilities.md`: subagents can spawn subagents (depth 3 by default, 20 concurrent); agent frontmatter supports model, effort, tools/disallowedTools, maxTurns, isolation: worktree, autoCompactWindow, etc.; plugins can ship agents, skills, hooks, MCP, scripts, bin; hooks list; statusline exposes context and rate limits (interactive only); agent teams exist but are experimental, interactive-only, store state in ~/.claude and do not isolate teammates → not used for now.
- `paseo-capabilities.md`: what Paseo offers (agents as sessions, heartbeats, handoff, `paseo usage`, plugin panels) — optional extras only.
- `task-trackers.md` + `tracker-bakeoff.md`: Backlog.md 1.55.3 passed all 8 hands-on scenarios (no ID collisions across worktrees of one repo, `on_status_change` hook fires from CLI and MCP, MCP server with 24 tools, clone-and-resume, JSON watch ~0.3 s, archive). Gaps and mitigations: claims are not atomic → mkdir-lock wrapper (`claim_backlog.sh` in the lab works); only PM/architect create tasks from one repo; no scope field → frontmatter `references`; `task list --json` omits deps/scope → `task view --json`; init with `--agent-instructions none`. beads is atomic but needs a Dolt remote to resume after clone, its hooks do not fire on Windows, and init writes many files and enables telemetry.
- `hooks-prototypes.md`: context % from the transcript works (last main-chain assistant usage: input + cache_read + cache_creation; 69 ms on 22 MB; window size must be an explicit setting); hook `additionalContext` warnings work (throttle per band); guided compaction works headless (`MSYS_NO_PATHCONV=1 claude -p "/compact …" --resume <id>`; PreCompact instructions honoured, SessionStart(compact) re-injects `.maestro/handoff.md`); nested agents: a level-1 agent receives level-2 results only if it stays active, otherwise they go to the root → the architect must stay active until its tasks return; SubagentStart/Stop fire at level 2 but carry no parent id; usage: statusline does not run headless, no CLI usage command, but `claude -p --output-format stream-json --verbose` emits `rate_limit_event` with five_hour and seven_day utilization (undocumented but official CLI output) → probe approach. Always pass `</dev/null` to `claude -p`. Forbid agents from changing permission mode (an attempt with bypassPermissions was refused by the classifier).
