# Comparable frameworks to Maestro

Date: 2026-11-06. Stars and last push come from the GitHub REST API (`api.github.com/repos/<owner>/<repo>`) on that date. Each fact links to its source. Anything not confirmed in a primary source (repo file, README or official docs) is marked **UNVERIFIED**.

Maestro, as used for comparison: a Claude Code plugin in which a PM main session leads architect subagents (one per GOAL, planning in waves). Each architect runs 2 implementers in their own git worktrees, with lock-based claims and one named test per given/when/then criterion. A black-box QA agent and a periodic fresh reviewer complete the team. State lives in git: Backlog.md, ADRs, owner decisions, `.maestro/events.jsonl` and a handoff file. Hooks cover context bands, usage probing and per-task measurement, and material decisions go to the owner. See `docs/plugin-contracts.md`.

## 2. Deep dives (the 5 most relevant, plus `team`)

### 2.1 GSD Core (open-gsd/gsd-core)

- **Roles:** 35 agents. Research and planning: project/phase/UI researchers, `gsd-planner`, `gsd-roadmapper`, `gsd-plan-checker`. Execution: `gsd-executor` ("atomic commits and deviation handling"), `gsd-verifier`, `gsd-integration-checker`, `gsd-nyquist-auditor` (fills test gaps), `gsd-security-auditor`. Review: `gsd-code-reviewer` and `gsd-code-fixer`. Also debugger, doc writers and a user profiler. [INVENTORY.md](https://github.com/open-gsd/gsd-core/blob/main/docs/INVENTORY.md)
- **Models:** `model_profile` = `quality | balanced (default) | budget | adaptive | inherit`, resolved per agent to `opus | sonnet | haiku | inherit`. [CONFIGURATION.md](https://github.com/open-gsd/gsd-core/blob/main/docs/CONFIGURATION.md), [ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/main/docs/ARCHITECTURE.md). The per-profile mapping is **UNVERIFIED** (not read).
- **Commands:** 72, including `/gsd-new-project`, `/gsd-discuss-phase`, `/gsd-plan-phase`, `/gsd-execute-phase`, `/gsd-verify-work` (conversational UAT), `/gsd-pause-work` (writes a handoff), `/gsd-resume-work`, `/gsd-progress`, `/gsd-ship` (PR plus review) and `/gsd-autonomous`. [INVENTORY.md](https://github.com/open-gsd/gsd-core/blob/main/docs/INVENTORY.md)
- **State:** `.planning/` holds `PROJECT.md`, `REQUIREMENTS.md`, `ROADMAP.md`, `STATE.md` ("Living memory: position, decisions, blockers, metrics"), `config.json`, and per phase `XX-CONTEXT.md`, `XX-RESEARCH.md`, `XX-YY-PLAN.md`, `XX-YY-SUMMARY.md`, `XX-VERIFICATION.md` and `XX-UAT.md`, plus `continue-here.md`. STATE.md writes use "lockfile-based mutual exclusion" with stale-lock detection after 10 s. [ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/main/docs/ARCHITECTURE.md)
- **Parallelism:** plans are grouped into dependency waves, run in parallel within a wave and sequentially across waves. Defaults are `max_concurrent_agents: 3` and `workflow.use_worktrees: true`. Parallel executors commit with `--no-verify` and the orchestrator runs pre-commit hooks once per wave. Several guards check the worktree base and HEAD before each wave. [ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/main/docs/ARCHITECTURE.md), [CONFIGURATION.md](https://github.com/open-gsd/gsd-core/blob/main/docs/CONFIGURATION.md), [INVENTORY.md](https://github.com/open-gsd/gsd-core/blob/main/docs/INVENTORY.md)
- **Human in the loop:** `mode: interactive` (default) or `yolo` ("auto-approves decisions"). There are four gate types (Confirm, Quality, Safety, Transition), `checkpoint:human-verify` before installing assumed or suspicious packages, and UAT as "the final gate". [CONFIGURATION.md](https://github.com/open-gsd/gsd-core/blob/main/docs/CONFIGURATION.md), [ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/main/docs/ARCHITECTURE.md)
- **Quality gates:** the plan-checker loops at most 3 times. A requirements coverage gate maps REQ-IDs to plans. A **decision coverage gate** checks CONTEXT.md decisions against plans (blocking) and against shipped artifacts (non-blocking). The verifier writes VERIFICATION.md and code review runs at `execute:post`. [ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/main/docs/ARCHITECTURE.md), [CONFIGURATION.md](https://github.com/open-gsd/gsd-core/blob/main/docs/CONFIGURATION.md)
- **Context:** "Every agent spawned by an orchestrator gets a clean context window." Hooks: `gsd-statusline.js` (context bar) and `gsd-context-monitor.js`, which warns at 35 % and 25 % *remaining*, debounced over 5 tool uses. There are also security hooks (`gsd-secret-read-guard.js` hard-blocks `.env`; prompt-injection scanners) and `gsd-validate-commit.sh` (conventional commits). [ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/main/docs/ARCHITECTURE.md), [hooks/](https://github.com/open-gsd/gsd-core/tree/main/hooks)
- **Install:** `npx @opengsd/gsd-core@latest` (installer asks for the runtime). Supports Claude Code, Codex, Copilot, Cursor and others. [README](https://github.com/open-gsd/gsd-core)
- **Maturity:** very active, large hook and test surface. The project moved from a single-author repo to an org fork in June 2026. [archived repo](https://github.com/gsd-build/get-shit-done)

### 2.2 Superpowers (obra/superpowers)

- **Roles:** no named agent files (no `agents/` dir; [repo root](https://github.com/obra/superpowers)). Roles are prompt templates inside skills: `implementer-prompt.md` and `task-reviewer-prompt.md`. [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- **Skills (workflow):** brainstorming → using-git-worktrees → writing-plans (tasks of 2-5 min) → subagent-driven-development or executing-plans → test-driven-development (deletes code written before its tests) → requesting-code-review ("Critical issues block progress") → finishing-a-development-branch (merge/PR/keep/discard plus worktree cleanup). [README](https://github.com/obra/superpowers)
- **Per-task loop:** a fresh implementer reports `DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED`. Only DONE gets a review package. A task reviewer returns two verdicts (spec compliance, then code quality), followed by a fix loop, a ledger line, and a whole-branch final review at the end. [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- **Models:** an explicit rule: the cheapest model for mechanical 1-2 file tasks, standard for integration, the most capable for architecture and the final review. Reviewers never go below mid-tier, fix rounds 4-5 escalate one tier, and every dispatch must name its model. [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- **Parallelism:** "Never dispatch multiple implementation subagents in parallel (conflicts)." The worktree is per branch, not per agent. [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- **State / context:** a git-ignored ledger, "because conversation memory does not survive compaction". Dispatch prompts carry only the task, its interfaces and global constraints ("Never make a subagent read the whole plan"). A `SessionStart` hook injects the bootstrap skill. [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [hooks.json](https://github.com/obra/superpowers/blob/main/hooks/hooks.json). The plan file location is **UNVERIFIED**.
- **Human in the loop:** the human signs off the design and says "go". After that the agent "decide[s] ambiguities itself and log[s] each decision as a ruling", stopping only for irreversible or destructive actions, security, external side effects (merge/push) or a broken plan. [README](https://github.com/obra/superpowers), [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- **Install:** `/plugin install superpowers@claude-plugins-official`, with separate installs for Gemini, Pi and others. [README](https://github.com/obra/superpowers)

### 2.3 oh-my-claudecode (OMC)

- **Roles / models (agent frontmatter):** 19 agent files, among them analyst, architect (opus), planner (opus), critic (opus), code-reviewer (opus), executor (sonnet), verifier (sonnet), qa-tester (sonnet), test-engineer, security-reviewer, debugger, git-master, writer and code-simplifier. [agents/](https://github.com/Yeachan-Heo/oh-my-claudecode/tree/main/agents), e.g. [executor.md](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/main/agents/executor.md). AGENTS.md lists further product roles (product-manager, ux-researcher). [AGENTS.md](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/main/AGENTS.md)
- **Modes / commands:** `/team` (canonical), `/autopilot`, `/execute`, `/ralph` (persistence), `/ralplan` (planning consensus), `/deep-interview`, `/omc-doctor`. CLI: `omc team N:provider` (tmux workers running codex/gemini/claude), `omc wait` (auto-resume after rate limits). [README](https://github.com/Yeachan-Heo/oh-my-claudecode)
- **Pipeline:** `team-plan → team-prd → team-exec → team-verify → team-fix (loop)`. Fix attempts are bounded, then the state becomes `failed`. The team resumes "from the last incomplete stage". Verifier depth scales with change size (<5 files lightweight, >20 thorough). [AGENTS.md](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/main/AGENTS.md)
- **Hooks (the broadest set seen):** UserPromptSubmit (keyword detector, skill injector), SessionStart (project memory, stale-run reporter, runs reconciler), PreToolUse (`git-guardrails`), PostToolUse (verifier, rules injector), SubagentStart/Stop (`subagent-tracker`, `verify-deliverables`), PreCompact (`pre-compact`, `project-memory-precompact`) and Stop (`context-guard-stop`, `workflow-drift-guard`, `persistent-mode`, `budget-guard`). [hooks.json](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/main/hooks/hooks.json). What `budget-guard` and `context-guard-stop` actually do is **UNVERIFIED** (only the names were read).
- **State:** `.omc/state/` (mode JSON), `.omc/notepad.md`, `.omc/project-memory.json`, `.omc/plans/`, `.omc/logs/`. Only `.omc/skills/**` is meant to be committed. [AGENTS.md](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/main/AGENTS.md), [README](https://github.com/Yeachan-Heo/oh-my-claudecode)
- **Worktrees:** native team-worker worktrees are "opt-in and still being added", and "deleting the worktree deletes its local OMC state". [README](https://github.com/Yeachan-Heo/oh-my-claudecode)
- **Cost:** model routing claims "30-50%" token savings (no methodology given; vendor claim). `omc wait` handles rate limits (needs tmux). [README](https://github.com/Yeachan-Heo/oh-my-claudecode)
- **Install:** plugin marketplace or `npm i -g oh-my-claude-sisyphus`, then `/omc-setup`. [README](https://github.com/Yeachan-Heo/oh-my-claudecode)

### 2.4 BMAD-METHOD

- **Roles (personas as skills):** Mary (Analyst), John (PM), Sofia (Product Owner: SPEC, TICKETS, BOARD, REPLAN), Winston (Architect), Amelia (Developer: build, QA, code review) and Sally (UX). Scrum Master and QA are no longer separate personas in the current docs. [skills-and-agents](https://docs.bmad-method.org/reference/skills-and-agents/). The test architect is a separate module (TEA). [docs](https://docs.bmad-method.org/)
- **Skills:** `bmad-build`, `bmad-build-auto` (unattended), `bmad-code-review`, `bmad-walkthrough` (human-guided review), `bmad-retrospective`, `bmad-qa-generate-e2e-tests`, `bmad-architecture`, `bmad-project-context`. [skills-and-agents](https://docs.bmad-method.org/reference/skills-and-agents/)
- **State:** the ticket tree is `tickets.toml`, edited through `tickets.py`. Each ticket has a plan file `<type>-<slug>-plan.md` whose frontmatter holds `status`, `baseline_revision`, `risk`, `deferred`, `blocked_reason`. Statuses: `draft → ready-for-dev → in-progress → in-review → built → done | blocked | dropped`. [autonomous loops](https://docs.bmad-method.org/build/autonomous-development-loops/). The older v6 `sprint-status.yaml` / story files appear only in third-party guides (**UNVERIFIED** for the current version).
- **Parallelism:** the orchestrator starts one worker per ticket in `ready_to_start`. "Independent epic streams can run in parallel when dependencies and integration boundaries are explicit". There is no worktree mechanism, and a clean tree is required. [autonomous loops](https://docs.bmad-method.org/build/autonomous-development-loops/)
- **Human in the loop:** per-ticket `plan_checkpoint` (a person approves the plan) and `done_checkpoint`. "Only a person or orchestrator marks a ticket done"; the worker stops at `built`. A review that finds an **intent gap** halts and saves the attempted change as a patch for a person. The repair loop stops after 5 non-converging iterations. [autonomous loops](https://docs.bmad-method.org/build/autonomous-development-loops/)
- **Install / maturity:** `npx bmad-method install` (v6.12 stable, needs Node 20.12+, Python 3.10+ and uv). V7 is a preview alpha installed as skills or plugin, with "breaking changes between updates". [README](https://github.com/bmad-code-org/BMAD-METHOD)

### 2.5 ccpm (Claude Code PM)

- **Form:** now one Agent Skill (`skill/ccpm/SKILL.md`) plus about 15 bash scripts. The old `/pm:*` commands live on branch `v1`. Phases: plan (PRD), structure (epic → numbered tasks with `depends_on`, `parallel`, `conflicts_with`), sync (GitHub Issues and sub-issues), execute and track. [README](https://github.com/automazeio/ccpm), [SKILL.md](https://github.com/automazeio/ccpm/blob/main/skill/ccpm/SKILL.md)
- **State:** "Files are the source of truth": `.claude/prds/`, `.claude/epics/<feature>/epic.md`, task files renamed to issue numbers, `<N>-analysis.md`, `updates/<N>/stream-<X>.md` and `execution.md`. Progress is posted as issue comments, and commits use the form `Issue #N: ...`. [README](https://github.com/automazeio/ccpm), [execute.md](https://github.com/automazeio/ccpm/blob/main/skill/ccpm/references/execute.md)
- **Parallelism:** **one worktree per epic** (`../epic-<name>/`) shared by several `general-purpose` agents, each limited to a file scope. Shared files go to one designated stream, conflicts are reported and the agent pauses, and force flags are banned. The README warns that agents sharing a worktree share one database (optional Neon branch per epic). [execute.md](https://github.com/automazeio/ccpm/blob/main/skill/ccpm/references/execute.md), [README](https://github.com/automazeio/ccpm)
- **Deterministic work:** `status.sh`, `standup.sh`, `next.sh`, `blocked.sh`, `validate.sh`, under the rule "always run the bash script directly rather than doing the work manually". [SKILL.md](https://github.com/automazeio/ccpm/blob/main/skill/ccpm/SKILL.md)
- **Human / quality:** confirmation at each phase ("Ready to push to GitHub?"), and an issue starts only when the user says "start issue N". There is no separate review gate. [README](https://github.com/automazeio/ccpm), [execute.md](https://github.com/automazeio/ccpm/blob/main/skill/ccpm/references/execute.md)
- **Install:** clone and symlink into `.claude/skills/`. Needs `gh`. [README](https://github.com/automazeio/ccpm)

### 2.6 bostonaholic/team (small, but closest in shape)

- **Pipeline:** WORKTREE → QUESTION → RESEARCH → DESIGN → STRUCTURE → PLAN → IMPLEMENT → CODE REVIEW → SECURITY REVIEW → PR. Artifacts go to `docs/plans/<id>/` (`1-task.md`, `2-questions.md`, `6-design.md`, `8-plan.md`, `review-<n>.md`). Live coordination uses TodoWrite. [README](https://github.com/bostonaholic/team)
- **Bias control:** "the questioner is the only agent that sees the original request", and researchers see only `2-questions.md`. Reviewers "hold no `Write` or `Edit` tool and run in `plan` mode". [README](https://github.com/bostonaholic/team)
- **Test first:** a test-architect writes failing tests, a mechanical gate checks them, then the implementer commits slice by slice. 4 parallel reviewers loop "until no Blocking or Major finding is left". [README](https://github.com/bostonaholic/team)
- **Models:** opus for implementer, test-architect, code-reviewer and planner; haiku for the verifier. [agents/](https://github.com/bostonaholic/team/tree/main/agents)
- **Human:** a single hard gate (an adversarial design review). "The orchestrator is forbidden from handing a blocking finding to the human mid-run." [README](https://github.com/bostonaholic/team)

## 3. Short notes on the others

- **wshobson/agents `agent-teams`:** team-lead, team-reviewer, team-debugger and team-implementer ("implements within strict file ownership boundaries"). Commands `/team-spawn`, `/team-feature`, `/team-review`, `/team-debug`, `/team-status`, `/team-shutdown`. Rule: "Never assign the same file to multiple implementers; use interface contracts at boundaries". Requires `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. [plugin](https://github.com/wshobson/agents/tree/main/plugins/agent-teams)
- **Claude Code agent teams (native):** a lead, teammates, a shared task list (file-locked claiming) and a mailbox, plus `TeammateIdle`, `TaskCreated` and `TaskCompleted` hooks (exit 2 blocks). Limitations: no resume of in-process teammates, "Task status can lag", one team per session, no nested teams, more tokens than subagents, and "Two teammates editing the same file leads to overwrites". [docs](https://code.claude.com/docs/en/agent-teams)
- **Subagent facts that matter to Maestro:** subagents may spawn subagents "up to three layers below the main conversation" (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`). A subagent's `isolation: worktree` is "branched by default from your default branch rather than the parent session's `HEAD`". [sub-agents docs](https://code.claude.com/docs/en/sub-agents)
- **spec-kit:** `/speckit-constitution`, `-specify`, `-plan`, `-tasks`, `-implement`, `-converge`, run "one at a time, reviewing each result before continuing". Installed with `uv tool install specify-cli`, with extensions and presets on top. No roles or parallel team. [README](https://github.com/github/spec-kit)
- **Taskmaster:** PRD → tasks (`parse-prd`, `next`, `expand`, `analyze-complexity`), MCP server, main/research/fallback models, can run through the Claude Code CLI. The full MCP tool set costs "~21,000 tokens" of context, so lean tool profiles exist. Last push 2026-04-28. [README](https://github.com/eyaltoledano/claude-task-master)
- **Backlog.md:** principle "one task = one context window = one PR". Workflow guides as MCP resources (`backlog://workflow/task-execution` …), a project-wide `definition_of_done` added to new tasks, cross-branch/worktree task tracking (`checkActiveBranches`), and `--json` read output. [README](https://github.com/MrLesk/Backlog.md)
- **ECC:** 71 agents, 314 skills, `memory-persistence` and `strategic-compact` hooks (`pre-compact.js`, `suggest-compact.js`), and a cap on SessionStart injection (`ECC_SESSION_START_MAX_CHARS`, default 8000). Warns that the plugin "advertises the installed catalog to the model" and advises selective install. [README](https://github.com/affaan-m/ECC)
- **ruflo:** "100+" agents, queen-led swarm topologies, AgentDB vector memory, 27 hooks, an optional `ruflo-cost-tracker` (budgets, alerts). Many performance figures are self-reported. [README](https://github.com/ruvnet/ruflo)
- **SuperClaude:** 30 `/sc:*` commands, 20 agents, 7 modes, a "PM Agent" for documentation and learning, `/save` and `/load` session memory. [README](https://github.com/SuperClaude-Org/SuperClaude_Framework)
- **agent-os:** discover, deploy and index standards, plus shape-spec. Its README describes no orchestration. [README](https://github.com/buildermethods/agent-os)
- **contains-studio/agents:** a catalogue of about 37 role agents (studio-producer, project-shipper, test-writer-fixer, sprint-prioritizer…) copied into `~/.claude/agents/`. No orchestration or state, and inactive since July 2025. [README](https://github.com/contains-studio/agents)

## 5. Ideas worth borrowing

1. **Decision coverage gate.** Check that every owner decision or ADR referenced by a GOAL is reflected in the task plans (blocking) and in the shipped result (advisory). Maestro already records decisions, so this check would be cheap to add. [GSD ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/main/docs/ARCHITECTURE.md)
2. **Structured implementer status.** `DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED`, with review triggered only on DONE. It maps cleanly onto Maestro task reports and retry counting. [Superpowers SDD](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
3. **Explicit model per dispatch, plus escalation.** A cheap model for mechanical tasks, a stronger one for review, and one tier up when stuck. This fits Maestro's retry ≤2 rule (escalate on retry 2) and its per-task cost measurement. [Superpowers SDD](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
4. **"Rulings" log for non-material ambiguities.** The agent decides minor ambiguities itself and logs each one, which keeps owner interruptions for material ones. It could be a `decision.ruling` event type in `events.jsonl`. [Superpowers SDD](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
5. **Intent-gap halt.** When review finds the task was read two ways, stop, save the patch, and ask the owner instead of reworking. "Only a person or orchestrator marks a ticket done." [BMAD autonomous loops](https://docs.bmad-method.org/build/autonomous-development-loops/)
6. **Reviewers without write tools, in plan mode.** Also hide the original request from researchers, which is the same idea as Maestro's code-blind QA. Apply it to the code-reviewer and QA agent files via `tools`/`disallowedTools`. [team README](https://github.com/bostonaholic/team)
7. **Run hooks once per wave.** Parallel implementers skip commit hooks and the integrator runs them once per wave, which avoids double runs and lock contention between worktrees. [GSD ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/main/docs/ARCHITECTURE.md)
8. **Worktree base and HEAD check at spawn.** The implementer refuses to work if its worktree is not on the expected goal-branch commit. [GSD INVENTORY.md](https://github.com/open-gsd/gsd-core/blob/main/docs/INVENTORY.md), [issue #683](https://github.com/open-gsd/gsd-core/issues/683)
9. **Deterministic scripts for read-and-report work.** Status, standup, next and blocked run as scripts, not LLM reasoning. Maestro's `maestro status` already does this; extend it to `next`/`blocked` for the architect. [ccpm SKILL.md](https://github.com/automazeio/ccpm/blob/main/skill/ccpm/SKILL.md)
10. **Shared-file owner stream.** Shared files (package.json, types, config) go to one task per wave, and the others rebase after. This is a planning rule for the architect. [ccpm execute.md](https://github.com/automazeio/ccpm/blob/main/skill/ccpm/references/execute.md), [wshobson agent-teams](https://github.com/wshobson/agents/tree/main/plugins/agent-teams)
11. **Backlog.md Definition of Done defaults.** Put "named test per AC passes" and "reviewer approved" in `definition_of_done` so every task gets them automatically. [Backlog.md README](https://github.com/MrLesk/Backlog.md)
12. **Secret-read guard hook.** Hard-block reads of `.env`/secrets by subagents. This is cheap and matters for unattended runs. [GSD hooks](https://github.com/open-gsd/gsd-core/tree/main/hooks)

## 6. Risks and pitfalls others hit

- **Token burn from per-task subagents and reviews.** One user reports that subagent-driven development used up the whole 5-hour budget on a simple plan. [superpowers #1152](https://github.com/obra/superpowers/issues/1152). Another reports a general slowdown from skill context. [#743](https://github.com/obra/superpowers/issues/743). Agent teams use "significantly more tokens". [docs](https://code.claude.com/docs/en/agent-teams). Maestro's usage bands and per-task measurement address this; keep a hard stop at the 95 % band.
- **Orchestrator context fills in autonomous mode.** GSD's orchestrator reached about 83 % context after planning plus partial execution, which forced a manual restart. Causes: inline discussion, prefetching all phases, and full subagent results returned to the orchestrator. [get-shit-done #2065](https://github.com/gsd-build/get-shit-done/issues/2065). This is relevant to Maestro's PM and architect sessions: keep subagent reports short and on file.
- **Worktree base mismatch.** Claude Code's `isolation: worktree` branches from the default branch, so executors ran without the plan files. [gsd-core #683](https://github.com/open-gsd/gsd-core/issues/683), confirmed by the [sub-agents docs](https://code.claude.com/docs/en/sub-agents). Maestro's own `maestro worktree <name> --goal <G>` avoids this, so do not switch to the `isolation` field.
- **Silent loss of human-in-the-loop.** After an update, GSD's questions were "auto-answered" (the AskUserQuestion dialog broke). [get-shit-done #803](https://github.com/gsd-build/get-shit-done/issues/803). Owner decisions should be recorded as events or files and checked, not assumed to have been asked.
- **Plans that over-specify code.** The executor ends up copy-pasting and has to "violate" the plan to improve it. [superpowers #895](https://github.com/obra/superpowers/issues/895). Maestro tasks should specify acceptance criteria and interfaces, not code.
- **State-root drift.** OMC left 104 `.omc/` directories (one inside `~/.ssh/`) because outside a git repo it fell back to the current directory. [OMC #3873](https://github.com/Yeachan-Heo/oh-my-claudecode/issues/3873). Maestro anchors to the git common dir and no-ops without `.maestro/config.json`; keep that.
- **Rate-limit classification.** A throttled usage API (wait) was treated like an exhausted quota (stop). [OMC #2745](https://github.com/Yeachan-Heo/oh-my-claudecode/issues/2745). Maestro's usage probe and StopFailure logging should distinguish the two.
- **Shared worktree per epic.** Several agents in one checkout also share a database and other runtime resources. [ccpm README](https://github.com/automazeio/ccpm). Maestro's one worktree per implementer is safer, but shared local services such as DBs and ports still need a convention.
- **Task-status lag and resume gaps in native agent teams.** "Teammates sometimes fail to mark tasks as completed", and `/resume` does not restore in-process teammates. [docs](https://code.claude.com/docs/en/agent-teams). This supports Maestro's choice of subagents plus a git-backed tracker.
- **Framework churn.** BMAD V7 warns of "breaking changes between updates" ([README](https://github.com/bmad-code-org/BMAD-METHOD)), GSD moved repos ([archived](https://github.com/gsd-build/get-shit-done)), and ccpm dropped its commands for one skill ([README](https://github.com/automazeio/ccpm)). Maestro pins Backlog.md (`backlogVersion`) for the same reason.

## 7. What seems unique to Maestro

None of the projects studied ships these (based on the sources read; absence in an unread doc is possible):

- **Code-blind exploratory QA** on a tagged snapshot, as a separate role. Others have UAT with the user (GSD), a qa-tester or verifier that reads code (OMC), or nothing.
- **Periodic fresh reviewer** triggered by a count (every 15 integrated tasks) or at GOAL end, separate from per-task review.
- **Per-task cost and time measurement from transcripts** (`task.measure`, with owner interventions and rework cycles), combined with a 5h/weekly usage probe. Others offer model routing (OMC, GSD) or an optional cost plugin (ruflo), not per-task accounting.
- **Two-level delegation (PM → architect per GOAL → implementers)**, where the PM stays the owner's only interlocutor. GSD, OMC and Superpowers all orchestrate from the main session.
- **Owner-decision governance:** material decisions go to the owner with options plus a recommendation and are stored in git. Others either confirm every step (ccpm, spec-kit, GSD interactive) or forbid mid-run escalation (team).
- **Append-only, git-merged event log** (`events.jsonl`, `merge=union`) as the audit trail across worktrees. OMC keeps logs but does not commit them.
- **One named test per given/when/then criterion**, with the reviewer reading tests before code. `team` writes tests first, but not mapped one-to-one to criteria.
