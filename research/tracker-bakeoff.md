## 3. Notable problems

Backlog.md
- Claim is a plain edit: simultaneous claims both succeed locally, collide only at merge (as a text conflict on `assignee`). Needs a wrapper/lock.
- Sequential ids are safe across worktrees of one repo but collide between independent clones/machines creating at the same time.
- `task list --json` lacks dependencies/scope; scope needs `references` or body convention (works, but not first class).
- AC checklist, statuses and milestone are well supported; hierarchy is one level (GOAL -> subtasks).
- `backlog init --agent-instructions claude,agents` appends a delimited block to an existing CLAUDE.md/AGENTS.md (checked: original text preserved, block between `<!-- BACKLOG.MD GUIDELINES START/END -->`). Resolves open point 4.

beads
- Task data is not in git. Clone-and-resume requires a Dolt remote plus `bd bootstrap`, which is fragile on Windows with local-path remotes (needs `file:///` URL).
- Script hooks are silently dead on Windows (exec-bit check).
- `bd init` is invasive: writes `.agents/skills/beads`, `.claude/settings.json` (SessionStart hook `bd prime --hook-json`), `.codex/*`, `.cursor/*`, AGENTS.md, appends to CLAUDE.md, sets `core.hooksPath=.beads/hooks`, auto-commits 19 files, adds `.gitignore` entries. It would collide with Maestro's own hooks/instructions.
- Anonymous telemetry ON by default (`metrics.endpoint` set in config.yaml; events queued in `~/.beads/eventsData` before I ran `bd metrics off`).
- 157 MB binary; MCP needs a Python stack with Windows pywin32 pitfalls; AC is not a checklist; fixed status set; worktrees share one DB so tasks do not follow branches (a feature when you want a shared board, a drawback for "branch contains its task state").
- Strengths confirmed: atomic claim with lease, hash ids with no collision, typed deps and `bd ready`, JSON with structured metadata, events journal, cell-level merging.

## 4. Windows quirks encountered

Backlog.md: CRLF warnings from git (`autocrlf=true`); files checked out in worktrees end up CRLF while CLI-written files are LF (mixed endings, harmless, no conflicts seen). Slugs sanitize odd titles (`..` kept in filename; avoid path-like titles). Hook command runs through a shell: `bash script.sh` worked. A stale global 1.53.0 shadows nothing unless PATH order is wrong; use local/explicit version. No locking issues, no long-path issues seen (filenames include slug; paths stayed short).
beads: exec-bit hooks, `git+E:/` URL bug in bootstrap, pywin32 in MCP, `taskkill` needed to stop things, 157 MB exe. No file-lock failures even with 3 concurrent writers (serialized by embedded Dolt). Git CRLF warnings same as above. No long-path problems at these depths.

## 6. Recommendation for Maestro

**Choose Backlog.md** (confirms the desk research), pinned to 1.55.x, installed project-local or via a pinned global.

Why: the only requirement beads wins is the atomic claim, which a 15-line wrapper replicates. Backlog wins where Maestro lives: plain markdown in git (clone-and-resume with zero extra steps, diffable, reviewable in PRs, per-branch task state), native AC checklist, milestone -> GOAL -> subtask mapping, `onStatusChange` hook that works on Windows and for MCP edits, JSON watch stream for the dashboard, simple archive with stable ids, MCP server in the same binary. beads' Dolt-out-of-git storage, Windows hook failure, bootstrap fragility, invasive init and telemetry make it a worse fit for a git-native, multi-PC plugin.

Required mitigations:
1. **Who creates tasks:** only PM/architect create tasks, from the main checkout or a worktree of the same repo (never from an independent clone/second PC while another is also creating; if that happens, run an ID-duplicate check before merge). Implementers only edit existing tasks.
2. **Claim wrapper** `maestro claim <id> <@agent>`: lock (mkdir under `.git/maestro-locks/`, which is shared by all worktrees) + verify status/assignee, then `backlog task edit`. Release/clear the lock on done/unclaim. Run claims against the main checkout, or commit and merge claim edits immediately; unlocked simultaneous edits yield a visible git conflict, never silent loss.
3. **Scope:** store as `references: ["scope:<glob>"]` (frontmatter, via `--ref`); the scheduler reads it with `task view <id> --json` or by parsing frontmatter (list JSON omits it). Same for dependencies.
4. **Statuses:** edit `statuses` in `backlog/config.yml` by hand once (`To Do, In Progress, In Review, QA, Done`); set `remoteOperations: false`.
5. **Events:** `on_status_change` key in `backlog/config.yml` calling a bash script that appends JSON to `.team/events.jsonl` (`merge=union`); fires for CLI and MCP. Not fired by hand-edited files, so agents must use CLI/MCP only.
6. **Dashboard:** `backlog task list --json --watch` for the board plus per-task `view --json` for deps/scope.
7. **Init:** `backlog init --defaults --integration-mode cli --agent-instructions none` (or `claude`; it appends, never overwrites) and keep Maestro's own instruction files authoritative.
8. If the Maestro design later needs lease-based claims and cross-machine shared state without git conflicts, beads remains the fallback, but only with a Dolt remote, `file:///` URLs on Windows, event journal polling instead of hooks, `bd init` flags reviewed, and `bd metrics off`.
